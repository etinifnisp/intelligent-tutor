1. EXECUTIVE SUMMARY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The jee_research project is a fully implemented, end-to-end data intelligence pipeline for JEE (Joint Entrance Examination) question paper research. It automates the acquisition, extraction, classification, analysis, and reporting of JEE Main and JEE Advanced question papers spanning the decade from 2015 to 2025.

As of the date of this report, the pipeline has been executed successfully and has produced a corpus of 6,567 classified questions extracted from papers across 10 years. The system is built entirely in Python 3.10+, uses a structured 5-phase pipeline with a dedicated orchestrator script, and is augmented by an agent intelligence layer that governs AI-driven classification and research behaviors.

The system covers six major functional areas:

Automated paper acquisition — via direct HTTP downloads, web scraping with multi-source fallbacks, and synthetic PDF generation for offline testing.

Text-based question extraction — from PDFs using PyMuPDF (imported as fitz), with per-page image extraction stored in a structured folder hierarchy across 140 paper folders.

Rule-based classification — of every extracted question across five dimensions: subject, chapter, topic, difficulty, and question type, enforced by a keyword-scoring engine.

Corpus-wide deep research — computing chapter frequency trends, difficulty shifts over time, and structural repetition patterns across all 10 years of data.

Multi-format report generation — producing an Excel workbook with 5 analytical sheets, strategic Markdown study briefs, and per-chapter solved examples.

Gemini-powered question solving — generating standalone HTML reports per paper with step-by-step solutions, rendered LaTeX mathematics, and annotated common mistakes.

3. PHASE 1 — ENVIRONMENT SETUP (setup_pipeline.py)

The setup phase is the entry point for any fresh deployment of the pipeline. It performs complete bootstrapping of the project environment with no manual steps required from the user.

Virtual Environment Creation

The script checks for the existence of the .venv/ directory in the project root. If absent, it creates a new Python virtual environment using the built-in venv module. If the directory already exists, it skips creation and logs that it was found. This makes the setup idempotent — it is safe to run multiple times without side effects.

Dependency Installation

The following Python packages are installed into the virtual environment using pip install -U (always upgrade to latest):

  httpx                   Async HTTP client for downloads and scraping
  pdfplumber              Secondary PDF text extraction library
  pymupdf                 Primary PDF parsing engine (imported as fitz)
  openpyxl                Excel workbook generation
  google-generativeai     Gemini API SDK for AI-powered question solving

Directory Scaffolding

The script creates all necessary runtime directories in a single pass:
  logs/, outputs/, papers/main/, papers/advanced/, extracted/images/

Each directory is created with parents=True and exist_ok=True so nested paths are handled in one call and no error is raised if they already exist.

Setup Manifest

On successful completion, the script writes outputs/setup_complete.json containing:
  - The path to the virtual environment Python executable
  - The resolved project root path
  - The list of all created directories
  - The list of installed dependency packages
  - A timestamp and success status

This JSON file serves as the phase-completion artifact that the orchestrator checks before proceeding to Phase 2.

Output Artifact: outputs/setup_complete.json

4. PHASE 2 — PAPER ACQUISITION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Paper acquisition is the most architecturally complex phase. It is implemented across four separate scripts, each handling a different acquisition strategy. Together they cover direct HTTP downloads, multi-source web scraping, Playwright-based JavaScript rendering, and synthetic PDF generation for offline testing.

4.1 ASYNC DOWNLOADER (download_papers.py)

This is the primary download script invoked by the pipeline orchestrator. It uses Python's asyncio and httpx for fully asynchronous, non-blocking downloads.

Year Range Handling
The script accepts a --years command-line argument (default: 2015-2025), generating a list of target years. For each year it targets both JEE Main (Shift 1 and Shift 2) and JEE Advanced (Paper 1 and Paper 2), configurable via the --exams flag.

Real Download Attempt
A REAL_PAPER_URLS dictionary stores hardcoded official and mirror URLs for years where known direct links exist (2023 and 2024). For each paper, the official link is tried first; if that fails, it falls back to a GitHub mirror URL.

Synthetic PDF Fallback
When real downloads fail, or when --sample mode is active, the generate_synthetic_pdf() function creates a realistic test PDF using reportlab. The synthetic paper contains:
  - A cover page with exam name, paper ID, duration, maximum marks, and instructions
  - Three subject sections (Physics, Chemistry, Mathematics)
  - Two questions per subject: one MCQ with four options and one Numerical/Integer question
  - All questions are real-style JEE problems with accurate answer options

This ensures the entire pipeline can be tested and validated offline without any network access.

CAPTCHA Detection
Every HTTP response is checked for Cloudflare challenge patterns, HTTP 403/429/503 status codes, and known bot-detection strings such as "cf-challenge", "just a moment", and "recaptcha". Blocked URLs are skipped with a log warning rather than being retried indefinitely.

Download Manifest
All outcomes are saved to outputs/download_manifest.json, recording the filename, year, exam type, source URL, file size in KB, and status for every targeted paper.

Output Artifact: outputs/download_manifest.json


4.2 PRODUCTION SCRAPER (scraper.py)

scraper.py is the production-grade web scraper designed for comprehensive acquisition of real JEE papers. It implements three distinct data source strategies with automatic fallback.

JEE Advanced — Official Archive
The scraper fetches the official jeeadv.ac.in/archive.html page and parses all anchor tags for PDF links matching year and paper number patterns. For papers from 2019 onwards, it filters for English-language variants. If the archive page is unavailable, it constructs direct URL patterns:
  - 2019 and later: jeeadv.ac.in/past_qps/{year}_{paper}_English.pdf
  - Before 2019: jeeadv.ac.in/past_qps/{year}_{paper}.pdf

JEE Main — MathonGo
The scraper fetches MathonGo's previous year question papers page and parses structured HTML tables using BeautifulSoup. For each row it extracts the paper name and download link, then uses parse_mathongo_desc() to extract year, session (month-based: Jan/Feb → S1, Apr/Jul/Sep → S2), and shift number from the description text using regular expressions.

JEE Main — Allen Career Institute Fallback
For papers not found on MathonGo, the scraper checks Allen Career Institute's previous year papers pages. Allen embeds PDF download URLs as base64-encoded JSON objects in data-action HTML attributes. The parse_allen_payloads() function decodes these, extracts subject-specific PDF URIs, and groups them by (year, session, date, shift). Since Allen provides Physics, Chemistry, and Mathematics as separate PDFs per shift, the merge_allen_group() function downloads all three and merges them into a single combined paper PDF using PyMuPDF's insert_pdf() method.

Rate Limiting and Reliability
All requests enforce a 2-second minimum delay via enforce_rate_limit(). Failed requests retry with exponential backoff (2s, 4s, 8s delays). User-Agent strings rotate from a pool of six real browser fingerprints. Up to 5 redirect hops are followed automatically, including Google Drive redirect resolution that reconstructs direct export download URLs from file IDs.

Output: Papers saved to papers/main/ and papers/advanced/


4.3 STANDALONE FULL DOWNLOADER (jee_downloader.py)

A self-contained, standalone downloader designed to run independently of the main pipeline. It targets the full 2016–2025 range with comprehensive hardcoded URL maps.

JEE Advanced Direct URLs
A JEE_ADVANCED_PAPERS dictionary maps every year from 2016 to 2025 to official PDF URLs from jeeadv.ac.in, covering both English and Hindi language variants for 2019 onwards. A separate JEE_ADVANCED_AAT dictionary covers Architecture Aptitude Test papers for the same year range (10 papers total).

JEE Main via Vedantu
A JEE_MAINS_PAGES list of over 110 entries maps every known (year, session, date, shift) combination from 2016 to 2025 to its corresponding Vedantu page URL. For each page, scrape_pdf_from_vedantu() first tries static BeautifulSoup scraping to find anchor href PDF links and script-tag embedded JSON URLs, then falls back to a Playwright headless browser session if the PDF link is JavaScript-rendered.

CLI Interface
Supports --only-advanced, --only-mains, --dry-run, and --output-dir flags for flexible targeted usage.


4.4 ZIP EXTRACTOR (unzip_papers.py)

Handles the case where papers are distributed as a ZIP archive (e.g., JEE_Papers.zip). The script accepts the zip path as a command-line argument, unpacks every PDF, identifies whether each paper is JEE Main or Advanced based on filename keywords, then renames each PDF to the project's standardized naming convention before placing it in the correct subdirectory:

  JEE Main:     JEE_MAIN_{year}_S{session}_Shift{shift}.pdf
  JEE Advanced: JEE_ADV_{year}_P{paper}.pdf

Logs are written to both logs/unzip_rename.log and logs/pipeline.log.

5. PHASE 3 — QUESTION EXTRACTION AND CLASSIFICATION (extract_questions.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This phase is the analytical core of the pipeline. It reads every downloaded PDF, extracts question text, classifies each question across five dimensions, and produces the central data asset consumed by all downstream phases.

PDF Scanning

The script scans both papers/main/ and papers/advanced/ for all PDF files. For each file, it infers the year using a regex match on the filename (pattern: 201[5-9] or 202[0-5]). It builds a full list of paper metadata — filename, year, exam type, subdirectory — before beginning any extraction.

Thread-Isolated PDF Parsing

Each PDF is processed in an isolated Python thread via threading.Thread with a hard 60-second timeout. If a PDF is corrupted, unusually large, or simply takes too long, the main thread resumes, logs a timeout warning, and records the paper in the skipped_papers list. This design prevents the pipeline from hanging on any single problematic file.

Inside each thread, the process_pdf_thread_func() function opens the PDF with PyMuPDF (fitz.open()) and processes every page:

Step 1 — Subject Context Detection
Each page's text is scanned line by line for section header patterns. If a line contains PHYSICS, CHEMISTRY, or MATHEMATICS (case-insensitive), the current subject context is updated and carried forward to all subsequent pages. This means a question deep inside a Physics section is correctly labelled as Physics even if the word does not appear in that individual question's text.

Step 2 — Question Boundary Splitting
Three regex strategies are applied in descending order of specificity:
  (a) Split on "Question:" markers — used in well-structured PDFs with explicit labels
  (b) Split on Q[1-9]. or Q.[1-9]. patterns — handles numbered question formats
  (c) Split on Roman numeral or letter sub-items like (i), (ii), (a), (b)
  (d) If none match but physics/math keywords are present, treat the entire page as one question

Rule-Based Classification (rule_based_classify)

Every extracted text block is passed to the rule_based_classify() function, which returns a classification dictionary with six fields.

Subject Assignment
If a section header established a subject context, that is used directly. Otherwise, keyword scoring is applied: a vocabulary of approximately 40 Chemistry keywords, 30 Math keywords, and 35 Physics keywords is scanned across the lowercased text. Each match scores 1.5 points for Chemistry and Math, 1.0 for Physics. The highest-scoring subject wins. If all scores are zero, Physics is assigned as the default.

Chapter and Topic Mapping
Nested keyword checks map question text to specific chapter and topic labels. Examples:
  "velocity" or "acceleration" in Physics → Chapter: Mechanics, Topic: Kinematics
  "capacitor" in Physics → Chapter: Electricity, Topic: Electrostatics and Capacitance
  "coordination" in Chemistry → Chapter: Inorganic, Topic: Coordination Compounds
  "matrix" in Mathematics → Chapter: Algebra, Topic: Matrices and Determinants
  "integral" in Mathematics → Chapter: Calculus, Topic: Integration

Difficulty Assignment
JEE Advanced questions default to Medium, escalating to Hard for questions containing discriminating terms like "extrema" or "capacitor". JEE Main questions default to Easy with limited upward adjustment for more complex wording.

Question Type Detection
The text is scanned for type markers: [MCQ-multiple], [Numerical], [Integer], Matrix-match. Marking schemes are assigned accordingly:
  MCQ-single: +4 / -1
  MCQ-multiple: +4 / -2
  Numerical: +4 / 0
  Integer: +4 / 0
  Matrix-match: +4 / 0

Corpus Construction

Each classified question becomes a JSON record with 13 fields: question_number (global sequential ID), paper_filename, year, exam_type, session, shift, subject, chapter, topic, difficulty, question_type, marks_positive, marks_negative, and raw_text. All records are sorted by year descending and question number ascending before being saved to outputs/jee_corpus.json.

6. PHASE 4 — DEEP RESEARCH AND TREND ANALYSIS (deep_research.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This phase consumes the classified corpus and performs multi-dimensional statistical analysis to surface actionable research insights, then writes a structured findings report referencing official syllabus sources and coaching institute recommendations.

Corpus Validation

Before any analysis begins, the script validates that the corpus contains data from at least 8 distinct years. If the threshold is not met, the phase halts with an error message. This guard ensures trend analysis is statistically meaningful and not computed from a sparse, recent-only dataset.

Frequency Analysis

The script computes separate frequency dictionaries for JEE_MAIN and JEE_ADVANCED, each keyed by "Subject - Chapter" strings. For every chapter it tracks:
  - Total question count across all years
  - Marks-weighted frequency (sum of marks_positive values)
  - Year-wise question count breakdown as a nested dictionary

Rising Frequency Trend Detection

For every (exam type, chapter) pair, two rolling averages are computed:
  avg_late:  average questions per year across 2023, 2024, and 2025
  avg_prior: average questions per year across 2020, 2021, and 2022

If avg_late divided by avg_prior exceeds 1.1 AND avg_late is greater than 0.5, the chapter is flagged as a Rising Trend topic. This list feeds directly into the Excel prediction engine in Phase 5.

Structural Pattern Analysis

The entire corpus is grouped by the combination of (subject, chapter, topic, question_type). Any combination appearing in 3 or more distinct years is flagged as a Repeating Structural Pattern — meaning the exam routinely tests that specific topic with the same question format. These patterns are the highest-confidence predictor of future questions. Each entry records the list of active years and the total frequency count.

Difficulty Shift Detection

For every (exam type, chapter) pair, the average difficulty scores of questions from 2015–2019 are compared against those from 2020–2025, using a numeric mapping: Easy = 1, Medium = 2, Hard = 3. A positive shift greater than 0.1 is recorded as a Difficulty Upward Shift. This flags chapters that have become meaningfully harder in recent years despite appearing at similar frequency.

Web Deep Search Synthesis

The script compiles a structured deep_search_report.md covering four research areas:

JEE Main Syllabus Changes (2023–2025)
The most impactful change was a significant reduction in the Chemistry syllabus aligned with 2024 NCERT textbook revisions. Removed chapters include: States of Matter, Surface Chemistry, s-Block Elements, Metallurgy, Hydrogen, Environmental Chemistry, Polymers, and Chemistry in Everyday Life. Physics lost Communication Systems and simplified Experimental Skills. Mathematics lost Mathematical Reasoning and Mathematical Induction. The 2025 pattern change is also documented: Section B now requires all numerical questions to be answered (no longer choose 5 of 10), and negative marking now applies to numerical value questions.

JEE Advanced Continuity
The Advanced syllabus for both 2024 and 2025 remains identical to its predecessor, maintaining the full breadth of content and emphasizing multi-concept synthesis and calculus-heavy derivations.

Expert Recommendations
Synthesized advisory content from ALLEN and Resonance covering top chapters: Modern Physics, Current Electricity and Electrostatics for Physics; Coordination Compounds, Chemical Kinetics, and GOC for Chemistry; Calculus, Vectors and 3D Geometry, and Matrices and Determinants for Mathematics.

Citations
National Testing Agency official bulletins (jeemain.nta.ac.in), JEE Advanced organizing IITs archive (jeeadv.ac.in), Careers360 Engineering Guides, and ALLEN Career Institute publications.

7. PHASE 5 — REPORT GENERATION (generate_report.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This phase transforms the raw corpus and research analysis into polished, ready-to-use reports for students and educators. It produces three distinct outputs: an Excel workbook, a strategic study brief, and a chapter-level mechanics report.

EXCEL WORKBOOK (jee_research_report.xlsx)

Built using openpyxl, the workbook contains five structured worksheets.

Sheet 1 — Chapter Heatmap
A matrix with chapters as rows and years as columns. Each cell contains the count of questions from that chapter in that year. Conditional colour-scale formatting is applied from light green (low frequency) to orange-red (high frequency), making high-yield chapters visually obvious. Panes are frozen at row 1 and all columns are auto-sized.

Sheet 2 — Subject Marks Trend
Similar matrix layout but cells contain the total marks_positive sum per subject per year, revealing which subject's mark contribution has grown or shrunk across the decade.

Sheet 3 — Top 50 Predicted Topics
Ranked list of the 50 most likely topics to appear in the next examination. Each topic's prediction score is computed as:

  Prediction Score = (question_count × 1.2) + (total_marks × 0.3) + score_boost

A bonus of +5.0 is added for topics active in both 2024 and 2025. Each row includes the subject, chapter, topic name, historical question count, total marks, trend label (Rising or Stable), computed prediction score, and a confidence score:
  0.85 — topics active in 8 or more years
  0.75 — topics active in 5 or more years
  0.60 — topics active in fewer than 5 years

Sheet 4 — Difficulty Distribution
Shows Easy, Medium, and Hard question counts per subject per year, enabling direct comparison of how each subject's difficulty profile has evolved over time.

Sheet 5 — Advanced vs Main Overlap
Cross-tabulates every (subject, chapter) pair by JEE Main count and JEE Advanced count, then classifies each as:
  Shared — appears in both exam types
  JEE Main Exclusive — only in JEE Main
  JEE Advanced Exclusive — only in JEE Advanced

This directly informs students preparing for both exams about which chapters demand the most attention.

Styling Applied to All Sheets
  - Dark navy headers (#1F4E78) with white bold text, center-aligned
  - Thin light-grey cell borders on all data rows
  - Frozen panes on row 1 in every sheet

8. PHASE 6 — AI-POWERED PAPER SOLVER (solve_papers.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

solve_papers.py is an optional standalone phase that consumes the classified corpus and generates fully solved, beautifully formatted HTML reports for each paper using the Google Gemini API.

Architecture

The solver groups all corpus questions by their source paper, using paper_filename as the grouping key. If a question has no filename recorded, it constructs a fallback key from the combination of year + exam_type + session + shift. It then iterates through each paper group, solving questions one by one.

Gemini Integration

For each question the solver constructs a structured prompt instructing Gemini to:
  - Identify the core concept being tested (1–2 sentences)
  - Produce a step-by-step LaTeX-formatted mathematical solution
  - State the final correct answer
  - List 1–2 common mistakes or conceptual traps to avoid

The API call uses google.genai.Client with the gemini-3.5-flash model and response_mime_type set to application/json to enforce structured JSON output. Retry logic applies exponential backoff over three attempts (2s, 4s, 8s delays). A 1-second pause between questions respects API rate limits.

Mock Mode

If GEMINI_API_KEY is not found in the environment or in a .env file, the solver automatically activates mock mode. Mock mode generates plausible placeholder solution data including a LaTeX math demonstration, making it possible to validate the full HTML generation workflow without an API key or incurring API costs.

Resume Logic

Before processing any paper, the solver checks whether outputs/solved/SOLVED_{paper_name}.html already exists. If so, the paper is skipped entirely. This makes the solver fully resumable: it can be interrupted at any point and restarted without reprocessing already-completed papers.

HTML Report Design

generate_html_solved_paper() produces a self-contained dark-mode HTML file per paper. Each file has no external runtime dependencies except Google Fonts and MathJax loaded via CDN.

Layout: A fixed 320px sidebar contains a scrollable index listing all questions with their subject and topic. The main content area renders one card per question.

Question Card Structure
  - Header: question number, subject badge (colour-coded blue/orange/green), chapter badge, difficulty badge (green/amber/red)
  - Question Text panel: the raw extracted text
  - Concept Tested panel: brief explanation of the underlying concept
  - Step-by-Step Solution panel: detailed mathematical solution
  - Final Answer panel: highlighted in green with a checkmark
  - Common Mistakes panel: highlighted in amber with a warning icon

Mathematics Rendering: The template includes a full MathJax 3 configuration supporting both inline dollar-sign delimiters and display double-dollar delimiters, so all LaTeX expressions render as properly typeset equations when opened in any browser.

Responsive Design: CSS media queries collapse the sidebar for screens under 768px width, making reports usable on mobile devices.

CLI Flags
  --paper <name>   Solve only one specific paper (supports partial, case-insensitive matching)
  --test           Limit to the first paper, first 3 questions only
  --mock           Force mock mode regardless of API key presence

Output: outputs/solved/SOLVED_{paper_stem}.html per paper

9. PIPELINE ORCHESTRATION (run_pipeline.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

run_pipeline.py is the single entry point that chains all five phases sequentially with fail-fast error handling and comprehensive logging.

Design Philosophy

The orchestrator invokes each phase script as a child process using subprocess.run() with the virtual environment's Python executable. This strict process isolation means every phase runs with exactly the same Python environment, and a crash or exception in one phase cannot corrupt the in-memory state of another. Phases communicate only through files on disk, making the entire pipeline auditable and debuggable at any stage.

Each phase is wrapped in the run_phase() helper function, which:
  - Constructs the subprocess command with the phase script path and arguments
  - Captures both stdout and stderr from the child process
  - Checks the exit code; if non-zero, logs the full stderr and halts the pipeline
  - If successful, echoes all stdout lines to the pipeline log with the phase name as prefix

Phase Execution Order

  Phase 1: setup_pipeline.py        Creates venv and installs all dependencies
  Phase 2: download_papers.py       Downloads or generates PDFs (--sample mode by default)
  Phase 3: extract_questions.py     Extracts text and classifies all questions
  Phase 4: deep_research.py         Runs frequency, trend, and pattern analysis
  Phase 5: generate_report.py       Generates Excel workbook and Markdown reports

Note: Phase 2 is invoked with --sample and --dir ./papers flags by default in the orchestrator, directing it to use synthetic PDF generation. For production runs against real papers, this flag would be removed and replaced with a real download invocation.

Logging

Every operation is logged to logs/pipeline.log with ISO 8601 timestamps. The log captures:
  - Pipeline start and end markers
  - Each phase start and completion
  - All stdout lines from each phase script, prefixed with the script name
  - Full stderr output on any failure, enabling immediate diagnosis

12. TECHNICAL STANDARDS AND CODE QUALITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The codebase consistently applies a set of engineering standards across all 10 scripts. These standards are codified in the agent rules file and are observable throughout the source.

Language and Runtime

All scripts target Python 3.10+ and use modern language features throughout: union type hints (str | None), generic type annotations (list[dict], tuple[int, str]), and pathlib-based filesystem operations are used consistently. The project runs inside a self-managed virtual environment created and maintained by setup_pipeline.py, keeping all dependencies isolated from the system Python installation.

Async Architecture

All network-bound operations use asyncio and httpx for non-blocking, concurrent execution. This applies to download_papers.py, scraper.py, and the Google Drive redirect resolver. The Windows event loop policy is explicitly set to WindowsSelectorEventLoopPolicy at each async entry point for correct behavior on Windows with Python 3.10.

Error Handling

No bare except clauses appear anywhere in the codebase. All exceptions are caught as "except Exception as e" with the error message explicitly logged. Network failures trigger retry loops with logged attempt counts. Thread timeouts are handled by checking thread.is_alive() after the join timeout expires. Every download function returns a boolean success flag so callers can chain fallback logic cleanly without exception propagation.

Logging

All scripts use a consistent log_message(log_file, message) helper that prepends an ISO 8601 timestamp to every line and writes it simultaneously to stdout and logs/pipeline.log. The scraper uses Python's built-in logging module with a proper Logger object supporting separate file and console handlers, making it compatible with external log aggregation and monitoring tools.

File I/O

Every file read and write uses "with open(...) as f:" context managers — no file handles are left open outside a context block. All paths are pathlib.Path objects exclusively; no string concatenation for paths appears anywhere. Output directories are created with mkdir(parents=True, exist_ok=True) before any write, preventing FileNotFoundError at runtime.

Security Practices

Every HTTP response is checked for CAPTCHA and Cloudflare challenge patterns before processing. Blocked URLs are skipped with a log warning. User-Agent strings rotate from a pool of six realistic browser fingerprints to reduce the risk of automated blocking. The Gemini API key is read exclusively from environment variables or a .env file and is never hardcoded in any script. No student personal data is collected or stored.

Resumability

All phases implement resume logic:
  - The downloader skips files that exist and are over 10KB in size
  - The extractor records skipped papers separately without aborting the run
  - The solver skips papers whose HTML output already exists
  This means every phase can be interrupted and safely restarted from the last successful position, with no risk of duplicate processing or data corruption.

Dependency Stack

  httpx                   Async HTTP client for all network operations
  pymupdf (fitz)          Primary PDF text and image extraction engine
  pdfplumber              Secondary PDF text extraction (listed as dependency)
  openpyxl                Excel workbook creation and formatting
  reportlab               Synthetic PDF generation for offline testing
  google-generativeai     Gemini API SDK for AI-powered question solving
  beautifulsoup4          HTML parsing in the scraper module
  playwright              Optional headless browser for JavaScript-rendered pages

All packages are installed with pip install -U (always upgrade to latest). No version pinning is applied in the current implementation; pinning specific versions is a recommended next step for production stability.
